## Задача 1: Кластеризация

### Предлагаемое решение

Для развёртывания, запуска и управления приложениями в микросервисной архитектуре предлагается использовать **Kubernetes** в связке с **Istio** (service mesh) и **Helm** для управления конфигурациями и деплоем. Для безопасного хранения чувствительных данных используется **HashiCorp Vault** (или встроенные Kubernetes Secrets с использованием Sealed Secrets).

| Компонент | Назначение |
|-----------|------------|
| **Kubernetes** | Оркестрация контейнеров, управление жизненным циклом, автомасштабирование, разделение ресурсов, конфигурирование через переменные окружения. |
| **Istio** | Обнаружение сервисов, маршрутизация трафика, балансировка, mTLS, наблюдаемость. |
| **Helm** | Управление пакетами приложений, шаблонизация манифестов, версионирование релизов. |
| **Vault / Sealed Secrets** | Хранение и управление секретами (пароли, ключи, токены). |

### Как обеспечиваются требования

1. **Поддержка контейнеров**  
   Kubernetes является стандартом де-факто для оркестрации контейнеров. Поддерживает Docker, containerd, CRI-O и другие runtime. Каждый микросервис упаковывается в контейнер и запускается как Pod.

2. **Обнаружение сервисов и маршрутизация запросов**  
   Istio предоставляет service mesh: автоматическое обнаружение сервисов через Kubernetes Service, гибкую маршрутизацию (по путям, заголовкам, версиям), балансировку нагрузки, retry, timeout, circuit breaking. Входящий трафик управляется через Istio Ingress Gateway.

3. **Горизонтальное масштабирование**  
   Kubernetes поддерживает горизонтальное масштабирование через ReplicaSet, Deployment. Количество реплик задаётся вручную или автоматически (HPA).

4. **Автоматическое масштабирование**  
   Horizontal Pod Autoscaler (HPA) масштабирует поды на основе CPU, памяти или custom-метрик. Vertical Pod Autoscaler (VPA) регулирует ресурсы подов. Также можно использовать KEDA для событийно-ориентированного масштабирования.

5. **Явное разделение ресурсов, доступных извне и внутри системы**  
   - Внутренние сервисы доступны через ClusterIP (только внутри кластера).  
   - Внешние через NodePort, LoadBalancer или Ingress.  
   - Istio Ingress Gateway контролирует входящий трафик, а Egress – исходящий.  
   - Network Policies ограничивают сетевой доступ между namespace/подами.  
   - Resource Quotas и Limit Ranges разделяют вычислительные ресурсы между командами/проектами.

6. **Конфигурирование приложений с помощью переменных среды**  
   Kubernetes позволяет задавать переменные окружения через ConfigMap и Secrets. ConfigMap хранит несекретные параметры, а Secrets – чувствительные данные (пароли, ключи). Secrets монтируются как переменные окружения или файлы.

7. **Безопасное хранение чувствительных данных**  
   - **Kubernetes Secrets** хранят секреты в etcd (можно включить шифрование).  
   - **Sealed Secrets** позволяют хранить зашифрованные секреты в Git.  
   - **HashiCorp Vault** предоставляет централизованное управление секретами, динамические секреты, аудит, интеграцию с Kubernetes через sidecar/init-контейнеры.

### Принципы взаимодействия

1. **Разработчик** описывает приложение в `Dockerfile`, Helm-чарт содержит Kubernetes-манифесты (Deployment, Service, ConfigMap, Secret).
2. **CI/CD пайплайн** собирает Docker-образ, публикует его в Registry, затем Helm обновляет релиз в кластере.
3. **Kubernetes** запускает поды, управляет репликами, прокидывает переменные окружения из ConfigMap/Secrets.
4. **Istio** автоматически обнаруживает новые сервисы, настраивает маршруты, применяет политики безопасности и наблюдаемость.
5. **HPA** мониторит метрики и масштабирует поды при необходимости.
6. **Ingress Gateway** принимает внешний трафик и маршрутизирует его внутрь mesh.

### Почему выбрана эта архитектура

- **Kubernetes** – самый распространённый оркестратор, поддерживаемый всеми облачными провайдерами (AWS EKS, Azure AKS, Google GKE, self-hosted). Обеспечивает все требования из коробки или с минимальными дополнениями.
- **Istio** добавляет продвинутую маршрутизацию и безопасность, которые необходимы для сложных микросервисных систем.
- **Helm** упрощает управление жизненным циклом приложений, повторяемость деплоев и версионирование.
- **Vault** решает задачу безопасного хранения секретов более гибко, чем нативные Kubernetes Secrets.

### Альтернативы

- **Docker Swarm** – проще, но ограничен в возможностях масштабирования и маршрутизации.
- **Nomad** – хорош, но менее распространён и имеет меньше интеграций.
- **AWS ECS** – удобно в AWS, но привязывает к вендору и не имеет богатых возможностей service mesh.

Таким образом, предложенное решение полностью закрывает все требования и является промышленным стандартом для микросервисной архитектуры.

## Задача 2: Распределённый кеш (необязательная)

### Предлагаемое решение

Для организации распределённого кеширования сессий пользователей предлагается развернуть **Redis Cluster** внутри кластера Kubernetes с использованием **Redis Operator** (например, Spotahome/Redis Operator или Redis Enterprise Operator). Это обеспечивает декларативное управление кластером, автоматическое восстановление после сбоев и горизонтальное масштабирование.

Для мониторинга и наблюдаемости используется стек **Prometheus + Grafana** с экспортером метрик Redis.

### Компоненты

| Компонент | Назначение |
|-----------|------------|
| **Redis Cluster** | Распределённое хранилище ключ-значение с шардированием (3 шарда) и репликацией (3 реплики на каждый шард). |
| **Redis Operator** | Управление жизненным циклом кластера: создание, обновление, масштабирование, автоматическое восстановление после отказов. |
| **StatefulSet + PVC** | Обеспечивают стабильные сетевые идентификаторы и постоянное хранение данных для каждой ноды Redis. |
| **Pod Anti-Affinity** | Гарантирует распределение реплик одного шарда по разным физическим узлам (Worker Nodes), что соответствует схеме с тремя VM. |
| **Prometheus + Grafana** | Сбор и визуализация метрик производительности (загрузка CPU, память, количество ключей, hit/miss ratio, задержки). |
| **HashiCorp Vault** | Хранение учётных данных (пароль Redis) и параметров подключения, передаваемых микросервисам через Vault Agent Injector. |

### Как обеспечиваются требования

#### Отказоустойчивость и высокая доступность

- Каждый шард имеет 3 реплики, распределённые по разным узлам кластера (благодаря podAntiAffinity). При выходе из строя мастер-ноды одна из реплик автоматически становится мастером (выборы через Redis Cluster failover).
- Потери данных минимизируются благодаря асинхронной репликации и настройкам `min-replicas-to-write` для гарантии записи на несколько реплик (опционально).

#### Горизонтальное масштабирование

- Redis Cluster поддерживает линейное масштабирование: можно добавлять новые шарды (увеличивая общее количество слотов) без остановки сервиса. Оператор позволяет изменять параметр `clusterSize` в CRD, автоматически перебалансируя слоты.
- Вертикальное масштабирование (увеличение ресурсов Pod'а) также возможно через изменение `resources` в StatefulSet.

#### Производительность и низкая задержка

- Данные хранятся в оперативной памяти, что обеспечивает микросекундные задержки.
- Шардирование распределяет нагрузку по трём мастер-нодам, увеличивая общую пропускную способность.
- Клиентские библиотеки (например, redis-py, Jedis) поддерживают интеллектуальную маршрутизацию запросов к нужному шарду, избегая лишних сетевых переходов.

#### Безопасность и изоляция

- Доступ к Redis ограничен сетевыми политиками Kubernetes (NetworkPolicy): только разрешённые микросервисы (например, auth-service, session-service) могут подключаться к кластеру.
- Для аутентификации используется пароль (хранится в Vault и инжектится в поды микросервисов).
- Istio обеспечивает mTLS-шифрование трафика между сервисами и Redis (если Redis настроен на приём TLS-соединений).
- Redis развёртывается в отдельном пространстве имён (`cache`), что дополнительно изолирует его от других компонентов.

#### Наблюдаемость и мониторинг

- Встроенный экспортер Redis (`redis_exporter`) собирает метрики (количество ключей, память, статус репликации, количество операций в секунду).
- Prometheus опрашивает экспортер, а Grafana отображает дашборды, позволяя отслеживать здоровье кластера и вовремя реагировать на перегрузки.
- Логирование осуществляется через стандартный вывод (stdout) и агрегируется в ELK / Loki.

#### Управление данными и персистентность

- Каждая нода Redis использует PersistentVolumeClaim с типом `ReadWriteOnce`, что гарантирует сохранность данных при перезапуске Pod'а или переносе на другой узел.
- Включена политика сохранения RDB-снимков и AOF (Append Only File) для восстановления после сбоев.

### Принципы взаимодействия с микросервисами

#### Обнаружение сервисов

- Для внутреннего общения нод используется Headless Service (`redis-cluster-headless`), который возвращает IP-адреса всех активных Pod'ов. Клиенты используют DNS-имена для получения списка узлов кластера.
- Для внешнего доступа из микросервисов создаётся ClusterIP Service (`redis-cluster`), который балансирует подключения между мастер-нодами. Клиентские библиотеки сами определяют текущих мастеров и перенаправляют запросы при необходимости.

#### Конфигурирование подключения

- Микросервисы получают параметры подключения (адрес сервиса, порт, пароль) из переменных окружения, которые инжектируются через Vault Agent Injector или Sealed Secrets на этапе деплоя.
- Пример переменных: `REDIS_HOST=redis-cluster.cache.svc.cluster.local`, `REDIS_PORT=6379`, `REDIS_PASSWORD=***`.

#### Кеширование сессий

- При аутентификации пользователя микросервис `auth-service` записывает в Redis данные сессии с TTL (время жизни).
- При последующих запросах другие сервисы (например, `profile-service`) читают сессию по ключу (обычно `session:<token>`). Если данные отсутствуют или истекли, микросервис инициирует повторную аутентификацию.
- Используется стратегия Cache-Aside: сначала проверка в кеше, при промахе – обращение к основной БД с последующей записью в кеш.

#### Масштабирование микросервисов и кеша

- При увеличении количества реплик микросервисов нагрузка на Redis распределяется равномерно.
- Если кеш становится узким местом, администратор может добавить четвёртый шард с помощью оператора (без остановки сервиса), и Redis автоматически перераспределит слоты.

### Почему выбрана эта архитектура

- **Redis Cluster** – промышленный стандарт для распределённого кеширования с поддержкой шардирования, репликации и автоматического восстановления. Он полностью покрывает требования по высокой доступности и масштабируемости.
- **Redis Operator** значительно упрощает управление сложным кластером в Kubernetes, автоматизируя рутинные задачи (создание, обновление, резервное копирование, перебалансировка).
- **StatefulSet + PVC** обеспечивают стабильность и персистентность, что критично для данных сессий.
- **Интеграция с Istio и Vault** позволяет бесшовно вписать кеш в существующую микросервисную экосистему, обеспечивая безопасность и наблюдаемость на всех уровнях.
- Использование трёх реплик на шард гарантирует, что даже при отказе двух узлов (при условии, что они относятся к разным шардам) кластер продолжит работу, а мастер будет переизбран.

### Альтернативы

- **Memcached** – более лёгкий кеш, но без встроенной репликации и шардирования (требуется клиентская балансировка), что усложняет отказоустойчивость.
- **Hazelcast** – распределённый in-memory data grid, но он тяжеловеснее Redis и менее распространён для задач кеширования сессий.
- **Amazon ElastiCache (Redis Cluster)** – управляемый сервис, удобный, но привязывает к AWS и может не подходить для мультиоблачных или on-premise сред.
- **Нативное решение Kubernetes StatefulSet без оператора** – потребовало бы ручного скриптинга для инициализации кластера и обработки failover, что повышает операционную сложность.

Таким образом, предложенное решение полностью отвечает требованиям по надёжности, производительности и управляемости, а также гармонично сочетается с общей архитектурой микросервисов.
