## Задача 1: API Gateway

### Сравнительная таблица решений

| Решение | Маршрутизация запросов | Проверка аутентификации | Терминация HTTPS | Управление конфигурацией | Дополнительные возможности |
|---------|------------------------|--------------------------|------------------|---------------------------|-----------------------------|
| **Kong** | Да, на основе маршрутов и сервисов (декларативно или через API) | Плагины: Key Auth, JWT, OAuth2, OpenID Connect | Да | Админ API, декларативные файлы, Ingress Controller для Kubernetes | Rate limiting, трансформация запросов/ответов, логирование, мониторинг, широкая экосистема плагинов |
| **NGINX Plus** | Да, через конфигурационные файлы (location, upstream) | Встроенный модуль JWT, внешняя аутентификация | Да | Конфигурационные файлы, API для динамического обновления (коммерческая версия) | Ограничение скорости, кэширование, балансировка, но меньше готовых интеграций для микросервисов |
| **Traefik** | Да, автоматически на основе правил (IngressRoute, file provider, docker labels) | Middleware: Basic Auth, Forward Auth, JWT (через плагины) | Да | YAML/TOML, CRD для Kubernetes, автоматическое обнаружение сервисов | Let's Encrypt автоматизация, observability, легковесность |
| **Envoy + Istio** | Да, через VirtualService (Istio), но сложнее | Через фильтры (JWT, ext_authz) | Да | Istio CRD, xDS API | Service mesh, mTLS, трассировка, продвинутая маршрутизация (canary, blue-green), но высокая сложность |
| **Tyk** | Да, через определение API и endpoints | Встроенные механизмы: JWT, OAuth2, Basic Auth, HMAC | Да | REST API, файлы, Kubernetes Operator | Quotas, versioning, аналитика, developer portal |
| **Apache APISIX** | Да, на основе маршрутов и upstream | Плагины: JWT, Key Auth, OAuth, OpenID | Да | etcd как хранилище конфигураций, Admin API, декларативно | Высокая производительность, динамическое обновление, множество плагинов |

### Выбор решения

**Рекомендую Kong API Gateway.**

### Обоснование выбора

1. **Маршрутизация запросов к нужному сервису на основе конфигурации**  
   Kong позволяет декларативно описывать маршруты и сервисы через YAML/JSON файлы или через Admin API. Это удобно для хранения конфигурации в системе контроля версий и автоматизации развертывания. Поддерживает гибкие правила: по пути, заголовкам, методам, хосту.

2. **Проверка аутентификационной информации**  
   Kong имеет богатый набор плагинов для аутентификации: Key Authentication, JWT, OAuth2, OpenID Connect, Basic Auth. Можно применять плагины глобально или на уровне отдельных маршрутов/сервисов. Это позволяет централизованно управлять доступом, не дублируя логику в каждом микросервисе.

3. **Обеспечение терминации HTTPS**  
   Kong полностью поддерживает TLS/SSL терминацию на gateway, включая работу с сертификатами, автоматическое обновление (при интеграции с cert-manager), возможность настройки TLS на уровне маршрута. Весь внешний трафик шифруется до Kong, а внутри сети может идти по HTTP или mTLS.

4. **Дополнительные преимущества**  
   - Зрелость и широкое сообщество.  
   - Множество готовых плагинов: rate limiting, request transformation, CORS, логирование, Prometheus-метрики, Zipkin/Jaeger трассировка.  
   - Поддержка Kubernetes через Kong Ingress Controller, что упрощает интеграцию в современную инфраструктуру.  
   - Гибкая модель развертывания: bare metal, виртуальные машины, контейнеры.  
   - Хорошая производительность (основан на NGINX/OpenResty) и горизонтальная масштабируемость.

5. **Критерии отказа от альтернатив**  
   - NGINX Plus: хорош как веб-сервер и reverse proxy, но менее удобен для управления API, меньше готовых интеграций с системами аутентификации.  
   - Traefik: отлично подходит для Kubernetes и автоматического обнаружения, но требует более тщательной настройки для сложных сценариев API-маршрутизации и не имеет такого богатого набора плагинов.  
   - Envoy/Istio: мощная service mesh, но избыточен, если требуется только API Gateway; высокая сложность внедрения и эксплуатации.  
   - Tyk и APISIX: хорошие конкуренты, но Kong имеет более развитую экосистему и документацию, а также сильную поддержку сообщества.

Таким образом, Kong лучше всего соответствует требованиям задачи и обеспечивает баланс между функциональностью, гибкостью и сложностью эксплуатации.

## Задача 2: Брокер сообщений

### Сравнительная таблица решений

| Брокер | Кластеризация | Хранение на диске | Скорость работы | Поддержка форматов | Разделение прав доступа | Простота эксплуатации |
|--------|---------------|-------------------|-----------------|--------------------|--------------------------|------------------------|
| **RabbitMQ** | Да, встроенная кластеризация, зеркалирование очередей | Да, сообщения могут сохраняться на диск (persistent) | Средняя (до десятков тысяч сообщений/с) | AMQP, MQTT, STOMP, HTTP | Гибкая модель: пользователи, виртуальные хосты, права на чтение/запись/конфигурирование | Относительно простая, зрелая, много документации |
| **Apache Kafka** | Да, распределённый лог, репликация | Да, все сообщения пишутся на диск (лог) | Очень высокая (сотни тысяч сообщений/с) | Бинарный протокол, поддерживает любые данные | ACL на топики, группы, транзакции | Сложная: требует ZooKeeper/KRaft, настройки репликации, мониторинга |
| **NATS / NATS JetStream** | Да, кластеризация и JetStream для сохранения | JetStream поддерживает хранение на диске | Очень высокая (миллионы сообщений/с в NATS core) | Текстовый протокол, поддерживает любые данные | Аккаунты, пользователи, права на субъекты (subject-level) | Очень простая, лёгкая |
| **Apache ActiveMQ** | Да, кластеризация, master/slave | Да, сообщения могут быть persistent (KahaDB, JDBC) | Средняя (зависит от конфигурации) | JMS, AMQP, MQTT, STOMP | Пользователи, группы, права на топики/очереди | Умеренная, но устаревающая |
| **Redis (Pub/Sub + Streams)** | Да, Redis Cluster | Да, Redis Streams могут сохранять на диск (RDB/AOF) | Очень высокая (в памяти) | Свой протокол, любые данные | Ограниченные: пароль, ACL для команд | Очень простая, но не полноценный брокер |
| **Apache Pulsar** | Да, распределённая архитектура (брокеры + bookies) | Да, хранение в bookies (диск) | Очень высокая | Свой протокол, любые данные | ACL, tenants, namespaces | Сложная, но менее чем Kafka |

### Выбор решения

**Рекомендую RabbitMQ.**

### Обоснование выбора

1. **Поддержка кластеризации для обеспечения надёжности**  
   RabbitMQ имеет встроенную кластеризацию и поддержку зеркалирования очередей, что позволяет достичь высокой доступности и надёжности доставки. При сбое узла сообщения не теряются.

2. **Хранение сообщений на диске в процессе доставки**  
   Сообщения можно пометить как persistent, и они будут записаны на диск до того, как попадут к потребителю. Это соответствует требованию хранения в процессе доставки.

3. **Высокая скорость работы**  
   RabbitMQ показывает достаточную производительность для большинства корпоративных сценариев (до 20-30 тыс. сообщений/с на узел), а при необходимости горизонтального масштабирования можно использовать шардирование.

4. **Поддержка различных форматов сообщений**  
   RabbitMQ поддерживает несколько протоколов: AMQP (основной), MQTT, STOMP, HTTP. Это позволяет использовать его в гетерогенных системах с разными клиентами. Формат тела сообщения произвольный (JSON, XML, binary и т.д.).

5. **Разделение прав доступа к различным потокам сообщений**  
   RabbitMQ предоставляет развитую модель авторизации: пользователи, виртуальные хосты (vhost), права на чтение, запись, конфигурирование на уровне очередей и обменников. Это позволяет точно разграничить доступ разных сервисов к своим потокам.

6. **Простота эксплуатации**  
   RabbitMQ имеет простую настройку, понятную архитектуру, зрелый веб-интерфейс управления и множество инструментов мониторинга (Prometheus, Grafana). Не требует дополнительных компонентов, таких как ZooKeeper (в отличие от Kafka). Это снижает порог входа и операционные затраты.

7. **Сравнение с альтернативами**  
   - Apache Kafka: слишком сложен и избыточен, если не требуется обработка огромных потоков с хранением истории; требует отдельного координатора, настройки репликации, управления партициями.  
   - NATS: очень быстрый и простой, но функция сохранения сообщений на диск (JetStream) появилась относительно недавно, а система прав менее детализирована для сценария с множеством сервисов.  
   - ActiveMQ: функциональный, но менее производителен и менее активно развивается, чем RabbitMQ.  
   - Redis: не является полноценным брокером, хранение на диске ограничено, нет сложной системы прав.  
   - Apache Pulsar: мощный, но чрезмерно сложный, требует развёртывания дополнительных компонентов (ZooKeeper, bookies).

Таким образом, RabbitMQ наилучшим образом сочетает все требования: надёжность, сохранность сообщений, достаточную скорость, гибкие форматы, управление правами и простоту эксплуатации. Именно его я рекомендую для построения микросервисной архитектуры в крупной компании.

## Задача 3: API Gateway (необязательная)

### Реализация

В качестве API Gateway использован **Nginx**. Он обеспечивает:

- маршрутизацию запросов к сервисам `security`, `uploader`, `minio`;
- проверку аутентификации через вызов `security GET /v1/token/validation` (директива `auth_request`);
- возможность терминации HTTPS (в конфигурации не включена, но легко добавляется).

### Состав

- `nginx` — API Gateway, слушает порт 80.
- `security` — сервис аутентификации (Flask + JWT).
- `uploader` — сервис загрузки файлов (Flask + Minio SDK).
- `minio` — объектное хранилище (S3 совместимое).
