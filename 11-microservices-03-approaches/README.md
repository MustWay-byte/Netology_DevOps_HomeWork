## Задача 1: Обеспечить разработку

### Предлагаемое решение

Для организации непрерывной интеграции и доставки (CI/CD) в микросервисной архитектуре предлагается использовать **GitLab** как облачную систему управления репозиториями и **Jenkins** как основной CI/CD-оркестратор. Взаимодействие между ними обеспечивается через вебхуки, а для хранения Docker-образов используется встроенный в GitLab Container Registry или отдельный Docker Registry (Nexus, Harbor).

### Состав решения

| Компонент | Назначение |
|-----------|------------|
| **GitLab** (облачная или self-hosted) | Система контроля версий Git, репозитории на каждый микросервис, встроенный Docker Registry, управление пользователями и правами доступа. |
| **Jenkins** (self-hosted или облачный) | Оркестрация сборок, тестов и деплоя. Обеспечивает гибкую настройку pipeline, параметризованные запуски, работу с агентами. |
| **Jenkins Agents** (на собственных серверах или в облаке) | Выполнение сборок в Docker-контейнерах с использованием кастомных образов. |
| **Vault / Jenkins Credentials** | Безопасное хранение секретов (пароли, ключи доступа). |
| **Docker Registry** | Хранение собранных Docker-образов. |

### Как обеспечиваются требования

| Требование | Реализация |
|------------|------------|
| **Облачная система** | GitLab может быть развёрнут как SaaS или как self-hosted в облаке. Jenkins также может быть развёрнут в облаке или на выделенных серверах. |
| **Система контроля версий Git** | GitLab полностью построен на Git и предоставляет удобный веб-интерфейс, merge requests, code review. |
| **Репозиторий на каждый сервис** | Каждый микросервис имеет отдельный репозиторий в GitLab. Это позволяет независимо развивать и деплоить сервисы. |
| **Запуск сборки по событию из системы контроля версий** | GitLab отправляет webhook в Jenkins при push, merge request или других событиях. Jenkins запускает соответствующий pipeline. |
| **Запуск сборки по кнопке с указанием параметров** | Jenkins поддерживает параметризованные сборки (Parameterized Builds): пользователь нажимает «Build with Parameters», вводит значения (например, тег версии, окружение) и запускает сборку. |
| **Возможность привязать настройки к каждой сборке** | В Jenkins можно создавать отдельные job или pipeline под каждый сервис, с индивидуальными настройками (переменные окружения, параметры, триггеры). |
| **Возможность создания шаблонов для различных конфигураций сборок** | Jenkins поддерживает: <br> – Jenkins Pipeline Shared Libraries – общие библиотеки с шагами и утилитами; <br> – Job DSL Plugin – описание job’ов как код, что позволяет генерировать множество похожих конфигураций; <br> – Jenkins Templates через кастомные скрипты. |
| **Возможность безопасного хранения секретных данных** | Jenkins имеет встроенный Credentials Plugin, который шифрует секреты и предоставляет их в pipeline как переменные. Дополнительно можно интегрировать HashiCorp Vault для централизованного управления секретами. |
| **Несколько конфигураций для сборки из одного репозитория** | Jenkins позволяет создать несколько job’ов или pipeline’ов, указывающих на один и тот же репозиторий, но с разными параметрами (например, сборка для dev, staging, production). Это реализуется через параметры и условия в pipeline. |
| **Кастомные шаги при сборке** | Jenkins Pipeline (Declarative или Scripted) предоставляет полную свободу: можно вызывать любые shell-команды, скрипты, Docker-контейнеры, внешние API. |
| **Собственные Docker-образы для сборки проектов** | Jenkins агенты могут запускаться в Docker-контейнерах на основе кастомных образов. В pipeline можно указать `agent { docker { image 'myregistry/my-build-image:latest' } }`. |
| **Возможность развернуть агентов сборки на собственных серверах** | Jenkins поддерживает master-agent архитектуру. Агенты можно ставить на любые серверы (Windows, Linux, macOS) и подключать к master через SSH или JNLP. |
| **Возможность параллельного запуска нескольких сборок** | Jenkins master может выполнять несколько сборок одновременно (по числу доступных executor’ов). Агенты могут быть распределены по разным машинам. |
| **Возможность параллельного запуска тестов** | В pipeline используется директива `parallel`, позволяющая запускать независимые стадии (например, unit-тесты, интеграционные тесты) одновременно на разных агентах. |

### Почему выбрана связка GitLab + Jenkins

- **GitLab** отлично закрывает потребности в хранении кода, управлении доступом, merge request и Docker Registry.
- **Jenkins** – самый гибкий и расширяемый CI/CD инструмент, который покрывает все требования: параметризованные запуски, шаблоны, кастомные шаги, собственные Docker-образы, агенты на своих серверах, параллелизм.
- В отличие от встроенного GitLab CI/CD, Jenkins предоставляет более тонкий контроль над пайплайнами, легче интегрируется с внешними системами и имеет огромную экосистему плагинов.
- Возможность использовать оба инструмента как в облаке, так и on-premise обеспечивает масштабируемость и отказоустойчивость.

### Альтернативные варианты

- **GitLab CI/CD** как единое решение (упрощает инфраструктуру, но менее гибок в кастомизации параметризованных сборок и использовании собственных агентов с уникальными настройками).
- **GitHub Actions + Jenkins** или **TeamCity** – возможны, но Jenkins остаётся наиболее универсальным для крупных enterprise-систем.

Таким образом, предлагаемое решение полностью соответствует всем заявленным требованиям и является оптимальным для крупной компании, строящей микросервисную архитектуру.

## Задача 2: Логи

### Предлагаемое решение

Для централизованного сбора, хранения и анализа логов микросервисов предлагается использовать стек **Elastic Stack (ELK)** с добавлением **Kafka** в качестве буфера для гарантированной доставки. Агентами на хостах выступают **Filebeat** или **Fluent Bit**.

| Компонент | Назначение |
|-----------|------------|
| **Filebeat / Fluent Bit** | Лёгкие агенты, устанавливаемые на каждом хосте. Читают логи контейнеров (stdout) и отправляют в Kafka/Logstash. |
| **Kafka** | Распределённый брокер сообщений, обеспечивает буферизацию и гарантированную доставку логов при пиковых нагрузках или сбоях. |
| **Logstash** | Принимает логи из Kafka, обрабатывает (парсинг, обогащение, фильтрация) и отправляет в Elasticsearch. |
| **Elasticsearch** | Централизованное хранилище и поисковый движок. Обеспечивает быстрый полнотекстовый поиск и агрегации. |
| **Kibana** | Веб-интерфейс для поиска, фильтрации, визуализации и создания сохранённых поисков с возможностью делиться ссылками. |

### Как обеспечиваются требования

| Требование | Реализация |
|------------|------------|
| **Сбор логов в центральное хранилище со всех хостов** | На каждом хосте запущен агент (Filebeat/Fluent Bit), который собирает логи всех контейнеров и передаёт их в центральную систему (Kafka + Logstash + Elasticsearch). |
| **Минимальные требования к приложениям, сбор логов из stdout** | Приложения просто пишут логи в стандартный вывод (stdout). Агенты читают Docker logs (или container runtime) без необходимости модификации кода. |
| **Гарантированная доставка логов до центрального хранилища** | Kafka обеспечивает надёжную буферизацию: сообщения сохраняются на диск и не теряются даже при временной недоступности Logstash или Elasticsearch. Filebeat/Fluent Bit поддерживают ретраи и подтверждение доставки. |
| **Обеспечение поиска и фильтрации по записям логов** | Elasticsearch предоставляет мощный полнотекстовый поиск, фильтры по полям, временным диапазонам, агрегации. |
| **Обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам** | Kibana имеет систему ролей и прав (RBAC), позволяет предоставить доступ разработчикам только к нужным индексам и дашбордам. |
| **Возможность дать ссылку на сохранённый поиск** | В Kibana можно сохранить поисковый запрос и поделиться ссылкой, которая включает контекст времени и фильтры. |

### Принципы взаимодействия

1. **Контейнеры микросервисов** пишут логи в stdout/stderr.
2. **Агенты на хостах** (Filebeat или Fluent Bit) автоматически обнаруживают логи всех контейнеров (через Docker API или файлы логов) и отправляют события в Kafka.
3. **Kafka** принимает логи, распределяет по партициям, реплицирует для отказоустойчивости и сохраняет на диск.
4. **Logstash** (или несколько экземпляров) читает из Kafka, выполняет нормализацию (например, разбор JSON, добавление полей `container_name`, `namespace`), обогащение и отправляет в Elasticsearch.
5. **Elasticsearch** индексирует логи (обычно по временным индексам, например `logs-2026.09.02`) и обеспечивает быстрый поиск.
6. **Kibana** подключается к Elasticsearch, предоставляет UI для поиска, визуализации, создания дашбордов и сохранённых поисков.

### Почему выбрана такая архитектура

- **Гарантированная доставка**: Kafka выступает как буфер, который защищает от потери логов при перегрузках или отказе систем.
- **Масштабируемость**: все компоненты (агенты, Kafka, Logstash, Elasticsearch) легко масштабируются горизонтально.
- **Гибкость**: Logstash позволяет выполнять любые преобразования, а Elasticsearch - сложные поисковые запросы.
- **Экосистема**: ELK является де-факто стандартом для логирования, имеет обширную документацию и поддержку сообщества.
- **Безопасность**: встроенные механизмы аутентификации и авторизации в Kibana/Elasticsearch позволяют разграничить доступ разработчиков.

### Альтернативы

- **Grafana Loki** — более лёгкое решение, но требует отдельного агента (Promtail) и менее богатый язык запросов по сравнению с Elasticsearch.
- **Graylog** — похож по возможностям, но меньшая гибкость в масштабировании и экосистема.

Таким образом, предлагаемый стек полностью удовлетворяет всем требованиям и является проверенным промышленным решением для сбора и анализа логов в микросервисной архитектуре.
